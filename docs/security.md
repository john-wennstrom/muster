# Security Model

Muster is a correctness-ready beta. Standard agent tools run directly on the host. Profiled host commands are brokered and audited; these controls do not provide operating-system process or network isolation.

## Trust boundary

Child agents default to the standard Pi tool sets: `read`, `grep`, `find`, and `ls` for read-only tasks; writers also get `bash`, `edit`, and `write`; validators get the read tools plus `write`. Global and per-slot child extension/tool configuration is honored. These standard tools execute directly in the child. Declared task paths are included in the prompt, but the broker does not enforce those paths for standard tools. Writer leases still serialize writing tasks.

The parent controller retains lifecycle and evidence checks. `muster_submit_scope` and `muster_submit_gate` submit structured evidence through the broker. Internal callers can explicitly select `toolMode: "brokered"` to use the restricted filesystem/command replacements.

The optional brokered command path enforces:

- authenticated broker requests and role-specific tool allowlists;
- canonical worktree and declared path checks;
- an active writer lease for source mutation;
- executable allowlists, argument-array spawning, and an explicit working directory;
- a minimal environment allowlist that excludes credentials by default;
- timeout, output, cancellation, and process-cleanup limits;
- preflight checks for authentication, elevated permissions, destructive operations, and external side effects, made by fixed rules and, when judgment is enabled, by judged categories that are added to the rule-produced ones and never replace them; and
- repository snapshots and a post-command diff audit before results can become accepted task evidence.

The implementation contracts are defined in [command-profile.ts](../src/tools/command-profile.ts) and [host-runner.ts](../src/tools/host-runner.ts).

## Residual risk

Approved commands execute on the host with the permissions of the current operating-system user. A process can access files outside the repository or communicate over the network when the host account and host configuration permit it. Environment minimization does not prevent a process from discovering credentials stored elsewhere on the host.

For commands routed through the audited host runner, repository diff auditing detects unauthorized repository changes after a command runs and rejects its evidence. Standard child `bash`, `edit`, and `write` operations do not receive that per-command audit. Auditing cannot undo non-repository filesystem changes, network requests, or other host side effects.

Controller-managed tasks classified as requiring authentication, elevated permission, destructive action, or an external side effect stop at a persisted manual checkpoint before execution. This controller check does not intercept arbitrary commands issued through the standard child `bash` tool.

## Judgment egress

The judgment layer answers narrow typed questions about a state through a hosted classifier from a third party ([TypeSafe](https://docs.typesafe.ai/api)). When it is enabled, **repository content leaves the machine** and is sent to that service. This is third-party egress, and it is separate from the model providers that Muster's agents use.

Judgment is off unless it is opted into. Both of these must be set, and with either absent nothing is sent and the harness behaves exactly as it does without judgment:

| Variable | Meaning |
| --- | --- |
| `MUSTER_JEV=1` | Enables judgment. Without it, decisions report that judgment is disabled. |
| `MUSTER_JEV_API_KEY` | The service credential. With the flag set but no key, decisions report that judgment is not configured. |
| `MUSTER_JEV_MODE` | Unset, or `enforce`: a decision that is confident enough acts. `shadow` evaluates and records a decision but never lets it change behavior. Any other value makes judgment unavailable rather than guessing. |

No decision has an enabling variable of its own: once these are set, every decision in the table below runs. Enforce is the default, so an operator who sets `MUSTER_JEV=1` and a key gets acting decisions; `MUSTER_JEV_MODE=shadow` is the way to observe first. A decision that can reduce work still needs confident answers to act and otherwise does what happens without judgment, and no decision can grant a permission or remove a manual checkpoint.

What the layer does before anything is sent:

- **Redaction is best-effort, not a guarantee.** Every string in a state is scrubbed of bearer credentials, credential-bearing command flags, `key: value` secrets, private key blocks, and secret-bearing URL query parameters, and the API key is scrubbed by value. Patterns cannot recognize every secret, so a secret in an unusual form can still be sent. Treat redaction as a second line of defense, not permission to send sensitive content.
- **Credential-bearing files are refused, not redacted.** Each call site declares the repository paths that contribute to its state. A request is refused, and nothing is sent, if any declared path is an environment file (`.env`, `.env.*`, `*.env`), a private key or certificate file (`*.pem`, `*.key`, `*.crt`, `*.p12`, SSH identity files, and similar), a package-registry authentication file (`.npmrc`, `.yarnrc`, `.pypirc`, `.netrc`, and similar), or a cloud or version-control credential file (`.aws/credentials`, `.git-credentials`, `.kube/config`, and similar). The layer can only check the paths a call site declares, so a call site that omits a path defeats this check.
- **The process environment is never included.** The layer accepts no environment from callers, so no environment variable can reach a state.
- **Size is bounded and states are never truncated.** A state plus its longest question above 32,000 tokens, or a state plus all questions above 64,000 tokens, is refused. Token counts are deliberately over-estimated. Callers excerpt; the layer does not cut content down to fit.
- **Requests use a pinned model version**, and a response from any other version is discarded.

Every decision is recorded in the change's run store with a digest of the redacted state, not the state itself. The API key is never written to a record, usage entry, or test fixture.

### Provider data handling

Read the provider's own terms before enabling judgment on proprietary code: the [privacy policy](https://typesafe.ai/legal/privacy-policy), the [data processing addendum](https://typesafe.ai/legal/data-processing), and the [master customer agreement](https://typesafe.ai/legal/mca). As published when this section was written, the addendum limits the provider's use of customer personal data to documented instructions and bars selling or sharing it, retention is described as "as long as necessary" for the purpose rather than as zero retention, and the customer agreement grants the provider a broad licence to process the data and queries a customer submits. Muster does not verify any of this. **Operators handling proprietary code should confirm their retention and licensing arrangement with the provider before enabling judgment.**

### Egress by call site

Each call site that is enabled sends a state, and this table names it. Judgment itself is enabled by `MUSTER_JEV=1` and `MUSTER_JEV_API_KEY`. A change that adds a call site adds its row in the same change; a call site with no row here must not ship. Each call site sends nothing unless judgment is enabled as described above.

| Decision | Also requires | State sent | Declared source paths |
| --- | --- | --- | --- |
| `change.triage` (change triage) | Nothing beyond judgment being enabled | Once per `/change propose` or `/change refine` that has no explicit `lane=` argument: the effective request text (on refinement this includes the previous review's required changes), the planning phase, and up to ten candidate source files retrieved by code from the request's identifiers, each with its repository path and an excerpt of at most 600 bytes. **This is the largest planning egress: it sends repository source excerpts.** Files the credential denylist names, ignored files, binary files, files over 2 MiB, and dependency directories are never candidates, and retrieval itself sends nothing. The service answers the request's disposition, four risk questions, whether the change is mechanical, how far it reaches, and two questions per candidate, and writes nothing. Its answers can only raise the change's lane on a confident risk, lower it to small when every risk and the reach are confidently judged, or, in enforce mode, skip the preflight agent for a confident proceed or a corroborated already-satisfied; anything else runs the agent. | The paths of every candidate. |
| `review.task_focus` (task review focus) | Nothing beyond judgment being enabled | The task contract (definition, requirements, and scenarios), an excerpt of the diff of at most 24,000 bytes cut at a file boundary together with the complete list of changed paths, the test output, the authorized read and write scopes, and the test-first evidence. **The test output is the field most likely to carry incidental secrets.** Redaction is applied to the whole state. If any changed path is named by the credential denylist, or the state is too large, nothing is sent and the reviewer runs with today's prompt. **In enforce mode this answer can skip a task's review**: only when every question is answered confidently with its good value, the lane permits reduced work (never the large lane), verification passed, the test-first evidence was accepted, the diff excerpt is complete, every changed path is in the task's write scope and none is denylisted, and it is the task's first attempt. A skipped review is recorded as skipped, on a judgment basis naming this decision's record, and final validation accepts it only under the same lane rule. Shadow mode runs the reviewer and records that it would have been skipped. | Every changed path in the diff. |
| `command.classification` (command classification) | Nothing beyond judgment being enabled | For each brokered host command that the rules, the version-control allowlist, and the command profile would allow, and that is not read-only: the executable, the arguments with secret patterns redacted (a credential flag's value is replaced), the working directory relative to the worktree, and the command profile. The environment and the content of any file are never sent, and a package script is judged by its name, not its body. A category other than none denies the command as a rule-produced category does, at any confidence; a command the rules refuse is never sent. Each judgment is bounded to 1.5 seconds, after which the command proceeds as it does without judgment. | None; no file content contributes to the state. |
| `review.extraction` (review extraction) | Nothing beyond judgment being enabled | Only when a planning reviewer's response is not valid structured output: the reviewer's response text, at most 24,000 bytes, and the candidate lines parsed from it (at most 60 lines of at most 400 characters). **The response is the reviewer's own prose and can quote repository content the reviewer read, including source and specification text.** Redaction is applied to the whole state. A response with no candidate lines, or over any of those limits, is never sent, and neither is a response that is valid structured output. The service classifies the reviewer's lines and writes none, and an extracted review is marked in its review artifact. | None; the state is the reviewer's text, so no repository path is available to check against the credential denylist. |
| `plan.lint` (plan lint semantic check) | Nothing beyond judgment being enabled | Once per `/change review`, only after deterministic lint passes and only for a task list of at most 40 tasks: an excerpt of the change summary from the proposal of at most 2,000 bytes; the requirement and scenario text from the delta specifications, excerpted to fit, with every name kept; and each task's description, dependencies, scopes (read and write), and verification commands. **Requirement and scenario text and task descriptions describe intended work and can quote repository content; verification commands can carry arguments.** Redaction is applied to the whole state. A state over the service's limits is never sent. The service answers questions about the text and writes none: findings are fixed templates filled in by code. On the small lane a clean, confident answer, or an unavailable service, approves the plan without a reviewer, and any finding or uncertain concern escalates the change to medium; on the medium and large lanes findings only reach the reviewer as unverified notes. | None; the state is planning text read from the change's artifacts, so no repository path is available to check against the credential denylist. |
| `task.recovery` (task recovery) | Nothing beyond judgment being enabled | After a task attempt ends without completing, once per failed attempt: the task's description, requirements, and scenarios; the change's lane; and the failure record, which is the attempt number, how it ended, the failure evidence (each excerpt at most 2,000 bytes), the command that reproduces it with its exit code and an output tail of at most 1,000 bytes, and the fix the builder said it made (at most 2,000 bytes). **Failure evidence and the output tail are command output, which is where secrets most often leak.** Redaction is applied to the failure text when it is recorded and to the whole state when it is sent. A state over the service's limits is never sent. The service answers one choice and one question and writes nothing: in enforce mode a confident answer can end the task blocked for a person, escalate the change to the next lane so it is reviewed again, or add one more attempt within the scheduler's limit of two, and never more. Anything else, every unavailable answer, and shadow mode leave the outcome as it would be without judgment. | None; the state is failure text held in memory, so no repository path is available to check against the credential denylist. |
| `review.triage` (review triage) | Nothing beyond judgment being enabled | Only when a planning review is requested after an approving full review, with no additional review instructions, a retained copy of the approved artifacts, and no change to any specification or the task list: the unified diffs of the proposal and the design against that retained copy (five lines of context, at most 16,000 bytes in total) and the approving review's recommendations. **The diffs are the change's own prose and can quote repository content, and the recommendations are the reviewer's own text.** No specification or task-list text is ever sent, and none is retained; the proposal and design text and a digest of every reviewed file are kept locally, at most three retentions per change, only when judgment is enabled. Redaction is applied to the whole state. A state over the limit is never sent. The service answers questions about the edit and writes nothing, but this is the one call site whose answer can decide whether a review runs: an edit judged immaterial with high confidence, and confidently not changing requirements, scenarios, tasks, scopes, or what the approval relied on, is carried forward as the previous approval, at most three edits in a row. Anything else, and every unavailable answer, runs the full review. A carried-forward review names its basis review, its count, and the judged answers in its review artifact, and the command says so. | None; the state is planning text held in memory, so no repository path is available to check against the credential denylist. |
| `routing.task_model` (task routing) | Nothing beyond judgment being enabled, and a lane that permits reduced work (never the large lane) | Once before each task's first builder attempt: the task's description, requirements, scenarios, read and write scopes, and verification commands. **No source code and no file content is sent**; a retry sends nothing. **Task descriptions describe intended work and can quote repository content, and verification commands can carry arguments.** Redaction is applied to the whole state. A state over the service's limits is never sent. The service answers questions about the task and writes nothing, but its answer can change which model does the work and how hard it thinks: a task judged confidently mechanical, confidently free of deep-reasoning, large-context, novel-design, security-boundary, and public-contract needs, and narrow in reach, gets low builder thinking and medium reviewer thinking; a mechanical, risk-free task of moderate reach gets medium builder thinking and high reviewer thinking. In enforce mode such a task also runs on the builder economy model, and is reviewed by the reviewer economy model, when the user configured them with `MUSTER_BUILDER_ECONOMY_MODEL` and `MUSTER_REVIEWER_ECONOMY_MODEL`. Anything else, every retry, every unavailable answer, and shadow mode use the configured builder thinking, a high reviewer, and the primary models, and no model is chosen that the user did not configure. One request serves both the builder and the reviewer of the task. | None; the state is task text held in memory, so no repository path is available to check against the credential denylist. |

## Future isolation

OCI or native process and network isolation is deferred to a non-blocking post-beta hardening milestone. The work remains behind the command-runner interface so role, broker, task, and evidence contracts do not need to change. See the [post-beta roadmap](roadmap.md).
